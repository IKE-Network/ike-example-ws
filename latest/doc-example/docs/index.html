This document exercises all features of the IKE documentation pipeline. It serves as both a comprehensive test vehicle for all 6 PDF renderers and a template for new documentation projects.

1. Introduction

The IKE documentation pipeline converts AsciiDoc source to:

  • HTML5 — multi-page with table of contents

  • Self-contained HTML — single file with embedded images

  • PDF via Prawn — built-in, free (asciidoctorj-pdf)

  • PDF via FOP — free, pure Java (DocBook → XSL-FO → PDF)

  • PDF via Prince XML — commercial CSS Paged Media

  • PDF via Antenna House — commercial CSS Paged Media

  • PDF via WeasyPrint — free Python-based CSS Paged Media

  • PDF via RenderX XEP — DocBook → XSL-FO → PDF

This document tests each feature across all renderers.

2. Koncept Macros

Koncept Notation

This document uses Koncept (with a K) to refer to formally identified terminology atoms — entities with a UUID, a position in the subsumption hierarchy, and a machine-readable definition. When you see , that is a specific, formally identified Koncept. The word "concept" (lowercase, no brackets) retains its ordinary English meaning.

2.1. Concept Design

The Concept record embodies key principles from SNOMED CT:

2.1.1. Immutability

Records provide immutable data structures, ensuring Koncepts cannot be modified after creation:

// Once created, this Koncept cannot be changed
Concept diabetes = new Concept(
    73211009L,
    "Diabetes mellitus (disorder)",
    "Diabetes mellitus",
    "A metabolic disorder..."
);

2.1.2. Validation

Compact constructors enforce business rules:

public Concept {
    if (conceptId <= 0) {
        throw new IllegalArgumentException("Concept ID must be positive");
    }
    // ... additional validation
}

2.1.3. Factory Methods

Specialized factory methods ensure correct semantic tag application:

// Automatically adds (finding) semantic tag
Concept finding = Concept.clinicalFinding(
    38341003L,
    "Hypertension",
    "High blood pressure",
    "Elevated arterial blood pressure"
);

2.2. Koncept Relationships

In a full implementation, Koncepts are connected through formal relationships. For example, is related to both and through subsumption, while its definition includes existential restrictions to and .

2.3. Description Logic Representation

SNOMED CT Koncepts can be expressed in description logic notation. The definition of is:

Diabetes mellitus ⊑ Endocrine disorder ⊓ Metabolic disorder ⊓
    ∃ finding-site.Pancreatic structure ⊓
    ∃ has-finding.Hyperglycemia

Where: * ⊑ represents subsumption (is-a) * ⊓ represents intersection (and) * ∃ represents existential restriction (some)

2.4. Primitive vs. Fully Defined

Type Definition Example

Primitive

Necessary conditions only

"A disease affecting the pancreas" (not sufficient — other diseases also affect pancreas)

Fully Defined

Necessary and sufficient conditions

"A metabolic disorder with hyperglycemia, caused by insulin deficiency or resistance"

The distinction is critical for automated classification. A fully defined Koncept like provides necessary and sufficient conditions, enabling a DL reasoner to infer its position in the hierarchy. A primitive Koncept like provides only necessary conditions — subsumption relationships must be asserted by human modelers.

The isPrimitive() method provides a simplified check:

if (concept.isPrimitive()) {
    // Handle incomplete definition
    // May need human review for classification
} else {
    // Fully defined — can be automatically classified
    // Description logic reasoner can infer relationships
}

2.5. Future Enhancements

The Koncept model could be extended with:

  • Relationship representation

  • Role groups for complex definitions

  • Effective time and versioning

  • Multiple language support

  • Reference set membership

  • Concrete domains (numeric values, strings)

5.6. Page Breaks

In PDF output, a new chapter (level-2 heading) forces a page break. This is controlled by the CSS rule h2 { page-break-before: always; } in the print stylesheet, and by the Prawn theme’s heading configuration.

5.7. Images

The pipeline supports inline SVG diagrams (rendered by Kroki) and raster images. SVG is preferred for scalability and print quality.
